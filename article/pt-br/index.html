Escrito para estranhos: o que o open source pode ensinar ao seu time

Todo contribuidor, seja um estranho, um estagiário novo, você daqui a seis meses ou um agente de IA, precisa da mesma coisa: contexto, escrito no repositório.

▶ Slides Código · nov. de 2026 · 9 min de leitura

O spike

Você pega um ticket pequeno. A mudança parece simples, mas cai num projeto que o seu time herdou. O time que criou aquilo não existe mais. Quem escreveu o código já saiu da empresa. Não tem documentação nenhuma, e o código é difícil de ler.

Então, antes da tarefa de verdade, a sprint ganha um spike: um tempo reservado só para entender como aquilo funciona.

Quase todo desenvolvedor já passou por esse spike. A pergunta mais interessante é o que acontece quando ele termina. Para onde vai tudo o que você aprendeu? Para a sua cabeça. Para uma mensagem no chat. Quase sempre, para lugar nenhum. A próxima pessoa que mexer naquele projeto vai pagar pelo mesmo spike de novo.

Projetos open source vivem essa situação todo santo dia. Mantenedores vão embora. Quem contribui é estranho, está em outro país, em outro fuso, muitas vezes escrevendo numa língua que não é a sua. Ninguém pode ir até a mesa do autor e perguntar. E, mesmo assim, tem projeto que roda há décadas.

Então como um projeto sobrevive quando todo mundo é um estranho?

Como estranhos constroem software juntos

Uma palavra faz muito trabalho neste artigo: contribuidor, qualquer pessoa que altera o projeto. Guarde essa palavra; mais para frente ela vai incluir alguém que não é uma pessoa.

  • Usuários usam o projeto.
  • Contribuidores alteram o projeto.
  • Mantenedores decidem o que entra.

Contribuidores chegam e vão embora, e o projeto precisa continuar funcionando sem eles. Por isso, no open source, quase toda mudança segue o mesmo caminho:

  • Issue: alguém descreve um problema ou uma ideia.
  • Discussão: as pessoas combinam o que fazer, antes de alguém escrever código.
  • Pull request: uma proposta. "Esta é a minha mudança, por favor puxe ela para dentro."
  • Checks automáticos: a mudança é compilada e testada antes de qualquer pessoa olhar para ela.
  • Review: um mantenedor lê, faz perguntas e pede ajustes.
  • Merge: a mudança entra na branch principal.
  • Release: uma nova versão chega a quem usa.

Cada etapa é escrita e assíncrona, porque precisa ser. Não tem corredor, não tem daily, não tem fuso em comum. No open source, se não está escrito, não existe. Escrever não é burocracia por lá; é o único jeito de conversar.

Times dentro de uma empresa têm corredor, e é exatamente por isso que pulam a parte de escrever. Aí o time muda, e o corredor vai junto. É assim que nasce o spike.

A porta de entrada

Um estranho aparece querendo ajudar. O que ele vê primeiro? Um bom repositório responde as perguntas antes de alguém perguntar, com alguns arquivos em lugares previsíveis.

Os exemplos abaixo vêm de um pequeno repositório modelo: um encurtador de URLs em .NET, com pouquíssimo código de propósito e tudo o que um contribuidor precisa em volta dele. Os arquivos dele estão em inglês, como costuma ser no open source.

README

O que é, por que existe e como rodar. Um bom teste: um estagiário consegue rodar o projeto no primeiro dia só com o README? No repositório modelo são dois comandos, sem banco, sem segredo e sem serviço para subir:

CONTRIBUTING

Como a gente trabalha aqui: como criar a branch, como rodar os testes, como é um bom pull request, onde tirar dúvida. O GitHub mostra o link para ele automaticamente quando alguém abre uma issue ou um pull request. O runtime do .NET coloca ali uma das suas regras mais importantes:

DON'T surprise us with big pull requests. Instead, file an issue and start a discussion so we can agree on a direction before you invest a large amount of time.

dotnet/runtime · CONTRIBUTING.md

Em outras palavras: não apareça com um pull request gigante de surpresa. Abra uma issue antes, para todo mundo concordar com a direção antes de você investir muito tempo.

GLOSSARY

As palavras deste projeto, e o que elas significam aqui. Sem glossário, "slug", "short code" e "target URL" querem dizer três coisas diferentes para três pessoas diferentes, e para cada agente de IA. O repositório modelo lista até as palavras que evita, e usa "short code" no lugar delas:

  • slug: costuma ser um caminho legível, escolhido por alguém (/meu-post). Nossos códigos são aleatórios.
  • alias: não suportamos códigos personalizados, e "alias" dá a entender que sim.
  • hash: os códigos não são derivados da URL (veja o ADR 0001 mais abaixo).
01-model-repo/GLOSSARY.md

Templates de issue e de pull request

Um template é o texto que o GitHub preenche automaticamente quando alguém abre uma issue ou um pull request. Ele funciona como um formulário que já faz as perguntas certas, então quem reporta um bug já responde o que o mantenedor ia perguntar de qualquer jeito.

Issue: o bug report do dotnet/runtime

  • Description
  • Reproduction Steps
  • Expected behavior
  • Actual behavior
  • Regression? · Known Workarounds · Configuration

Pull request: o do repositório modelo

  • What and why
  • How to test
  • Checklist: testes, docs, CHANGELOG, ADR

Ninguém precisa lembrar o que perguntar. O formulário lembra.

CODEOWNERS

Quem precisa revisar mudanças em qual pasta. O próprio pull request pede review das pessoas certas, então ninguém precisa saber quem marcar. Do runtime do .NET:

/src/coreclr/jit/     @dotnet/jit-contrib
/.github/workflows/   @jeffhandley @dotnet/runtime-infrastructure
dotnet/runtime · .github/CODEOWNERS

Guarde uma ideia para depois: cada um desses arquivos também é lido por agentes de IA.

A memória do projeto

De volta ao spike. Ele nunca foi sobre o que o código faz; isso dá para descobrir lendo. Ele era sobre por que o código é do jeito que é. Código não guarda o porquê. Pessoas guardam, e pessoas vão embora.

docs/

Um arquivo por assunto: arquitetura, API, configuração, troubleshooting. Arquivo pequeno é arquivo que as pessoas encontram e atualizam. Uma página enorme na wiki é uma página em que ninguém confia.

Architecture Decision Records

Um ADR é um arquivo curto que registra uma decisão. O formato original, de Michael Nygard, tem cinco partes: Título, Status, Contexto (o problema e as forças envolvidas), Decisão e Consequências (o que fica mais fácil e o que fica mais difícil). Projetos como o Arachne mantêm os seus em público.

O primeiro ADR do repositório modelo explica como os short codes são gerados:

O registro completo também lista as opções que perderam (IDs sequenciais dá para adivinhar, hashes colidem e vazam URLs, GUIDs não têm nada de "short") e as consequências. Com isso escrito, ninguém "conserta" o retry achando que é bug.

A regra mais importante: um ADR aceito nunca é editado para mudar a decisão. Um novo ADR substitui o antigo. Esse rastro de decisões, com o motivo de cada uma, é exatamente o que o spike estava procurando.

Quem consome a API recebe atributos [Description] nos contratos, que vão parar no documento OpenAPI:

Nos dois casos, a documentação fica em cima da coisa que ela descreve, então muda no mesmo diff. Essa é a regra que faz tudo funcionar: a documentação no repositório é revisada no mesmo pull request que o código. A wiki apodrece em silêncio. A doc num pull request tem um revisor perguntando: "você atualizou isso aqui?"

Deixe a máquina dizer não

Até aqui, tudo depende de as pessoas fazerem a coisa certa. O open source não conta com isso, e não é por cinismo. Imagine um mantenedor recebendo um pull request de um completo estranho. Você faria o merge sem saber nem se compila?

Checks depois do merge

O problema aparece quando já está na main e todo mundo já puxou.

Checks no pull request

O problema aparece enquanto ainda é a branch de uma pessoa. Vermelho quer dizer que não dá merge.

Rodar os checks no pull request tem dois efeitos colaterais. O revisor nunca precisa ser o chato da formatação ou do teste quebrado, porque a máquina já disse não. E com required checks a plataforma obriga a regra, então ninguém precisa lembrar dela.

O CI do repositório modelo roda em todo pull request para a main:

Ele compila tratando warnings como erros (um XML doc comment faltando quebra o build), verifica a formatação e roda os testes, inclusive testes que checam a própria documentação da API. Tire um [Description] e o pull request fica vermelho:

Failed Every_contract_property_is_described
  LinkResponse.shortUrl has no [Description].

A documentação passa a fazer parte do "pronto", e quem diz não é a máquina.

Cultura de review

Com a parte chata automatizada, o review humano pode focar no que as pessoas fazem bem:

  • Pull requests pequenos. O pull request de 2.000 linhas de um estranho não é revisado; é ignorado.
  • Revise o código, não a pessoa. "Este método…", e não "você…".
  • Rotule o feedback, para quem escreveu saber o que bloqueia. O Conventional Comments faz isso com um prefixo em cada comentário:
issue (blocking): this accepts javascript: URLs.
suggestion: extract this into a method?
nitpick (non-blocking): extra blank line.

Os rótulos acabam com a adivinhação, principalmente entre pessoas escrevendo numa segunda língua. E quando o contribuidor é um agente de IA, é esse review que pega os erros dele.

Agentes de IA também são contribuidores

É aqui que a palavra contribuidor mostra para que veio: um contribuidor pode ser uma pessoa ou um agente. E um agente é o recém-chegado definitivo, com zero contexto, toda vez. Ele não lembra da conversa de ontem. Toda sessão é o primeiro dia dele.

Um agente é um estagiário com energia infinita e nenhuma memória. Então tudo o que ajuda um estranho (README, CONTRIBUTING, GLOSSARY, docs/ e ADRs) também é contexto pro agente. Um agente que leu o ADR 0001 não vai "simplificar" o retry e jogar ele fora.

AGENTS.md

O AGENTS.md se descreve como "a simple, open format for guiding coding agents": um formato simples e aberto para orientar agentes de código. Pense nele como o CONTRIBUTING dos agentes: como compilar, como testar, as convenções e o que não mexer. Arquivos específicos de cada ferramenta, como .github/copilot-instructions.md ou CLAUDE.md, só apontam para ele, para que as instruções não fiquem cada uma dizendo uma coisa. Contexto, comportamento esperado e critérios de aceite deixam uma issue pronta para qualquer um trabalhar nela, pessoa ou agente. O template de feature do repositório modelo pede isso explicitamente:

Os checks da seção anterior pegam os erros de um agente do mesmo jeito que pegam os nossos. Agentes abrem mais pull requests, então checks automáticos importam mais, e não menos.

Um alerta: instruções geradas a partir do código são um ótimo começo, mas elas envelhecem. Revise essas instruções como código, e atualize no mesmo pull request da mudança que elas descrevem.

Trazendo para casa

Nada disso é exclusividade do open source. Tem até nome: inner source, usar práticas de open source dentro de uma empresa, termo criado por Tim O'Reilly em 2000.

De volta ao spike uma última vez. O resultado de um spike não deveria ser uma resposta na cabeça de alguém. Deveria ser um arquivo em docs/, um novo ADR ou uma entrada no glossário, commitado. O repositório modelo transforma isso em regra:

Por onde começar, mais ou menos em ordem de esforço:

  1. Um README que faz um recém-chegado rodar o projeto.
  2. Um CONTRIBUTING: como a gente trabalha aqui.
  3. Checks no pull request, antes do merge.
  4. docs/ e ADRs, alimentados pelos seus spikes.
  5. Um GLOSSARY.
  6. Um AGENTS.md.

Não faça tudo. Comece com um arquivo, em um repositório, na próxima vez que você mexer nele. O repositório modelo está aí para servir de ponto de partida.

Um estranho, um estagiário novo, você daqui a seis meses, um agente de IA: todo contribuidor precisa da mesma coisa, contexto escrito no repositório. Escreva para estranhos. Cedo ou tarde, todo mundo é um.
