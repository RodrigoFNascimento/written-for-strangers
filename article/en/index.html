Written for Strangers: what open source can teach your team

Every contributor, whether a stranger, a new intern, you in six months or an AI agent, needs the same thing: context, written down in the repository.

▶ Slides (pt-BR) Code · Nov 2026 · 9 min read

The spike

You pick up a small ticket. The change itself looks easy, but it lands on a project your team inherited. The team that built it no longer exists. The people who wrote it have left the company. There is no documentation, and the code is hard to read.

So before the real task, the sprint gets a spike: time set aside just to understand how the thing works.

Most developers have been on that spike. The more interesting question is what happens when it ends. Where does everything you learned go? Into your head. Into a chat message. Usually, nowhere. The next person to touch that project pays for the same spike again.

Open-source projects live this situation every single day. Maintainers leave. Contributors are strangers, in other countries and other time zones, often writing in a second language. Nobody can walk over to the author's desk and ask. And yet some of these projects have been running for decades.

So how does a project survive when everyone is a stranger?

How strangers build software together

One word does a lot of work in this article: contributor, anyone who changes the project. Keep it in mind; later it will include someone who isn't a person.

  • Users use the project.
  • Contributors change it.
  • Maintainers decide what gets in.

Contributors come and go, and the project has to keep working without them. That is why open source sends almost every change down the same path:

  • Issue: someone describes a problem or an idea.
  • Discussion: people agree on what to do, before anyone writes code.
  • Pull request: a proposal. "Here is my change, please pull it in."
  • Automated checks: the change is built and tested before any human looks at it.
  • Review: a maintainer reads it, asks questions and requests changes.
  • Merge: the change goes into the main branch.
  • Release: a new version reaches the people who use it.

Every step is written and asynchronous, because it has to be. There is no hallway, no daily stand-up, no shared time zone. In open source, if it isn't written, it doesn't exist. Writing things down isn't bureaucracy there; it's the only way to talk.

Teams inside a company do have a hallway, and that is exactly why they skip writing things down. Then the team moves on, and the hallway goes with it. That's how you end up with the spike.

The front door

A stranger shows up wanting to help. What do they see first? A good repository answers their questions before they ask, with a handful of files in predictable places.

The examples below come from a small model repository: a URL shortener written in .NET, with deliberately little code and everything a contributor needs around it.

README

What this is, why it exists, and how to run it. A useful test: could a new intern run the project on day one with only the README? In the model repository it takes two commands, with no database, secrets or services to set up:

CONTRIBUTING

How we work here: how to branch, how to run the tests, what a good pull request looks like, where to ask. GitHub links to it automatically when someone opens an issue or a pull request. The .NET runtime puts one of its most important rules right there:

DON'T surprise us with big pull requests. Instead, file an issue and start a discussion so we can agree on a direction before you invest a large amount of time.

dotnet/runtime · CONTRIBUTING.md

GLOSSARY

The words this project uses, and what they mean here. Without one, "slug", "short code" and "target URL" mean three different things to three different people, and to every AI agent. The model repository even lists the words it avoids, and says "short code" instead:

  • slug: usually means a readable, human-chosen path (/my-blog-post). Our codes are random.
  • alias: we don't support custom codes, and "alias" suggests we do.
  • hash: codes aren't derived from the URL (see ADR 0001 below).

Issue and pull request templates

A template is the text GitHub fills in automatically when someone opens an issue or a pull request. It works like a form that already asks the right questions, so the person reporting a bug answers what the maintainer would have asked anyway.

Issue: dotnet/runtime's bug report

  • Description
  • Reproduction Steps
  • Expected behavior
  • Actual behavior
  • Regression? · Known Workarounds · Configuration

Pull request: the model repository

  • What and why
  • How to test
  • Checklist: tests, docs, CHANGELOG, ADR

Nobody has to remember what to ask. The form remembers.

CODEOWNERS

Who must review changes to which folder. The pull request requests reviews from the right people on its own, so nobody has to know who to ping. From the .NET runtime:

/src/coreclr/jit/     @dotnet/jit-contrib
/.github/workflows/   @jeffhandley @dotnet/runtime-infrastructure
dotnet/runtime · .github/CODEOWNERS

Hold one thought for later: every one of these files is also read by AI agents.

The project's memory

Back to the spike. It was never really about what the code does; you can find that out by reading it. It was about why the code is the way it is. Code doesn't keep the why. People do, and people leave.

docs/

One file per topic: architecture, the API, configuration, troubleshooting. Small files are files people actually find and update. One huge wiki page is a page nobody trusts.

Architecture Decision Records

An ADR is a short file that records one decision. Michael Nygard's original format has five parts: Title, Status, Context (the problem and the forces at play), Decision, and Consequences (what gets easier and what gets harder). Projects like Arachne keep theirs in public.

The model repository's first ADR explains how short codes are generated:

The full record also lists the options that lost (sequential IDs are guessable, hashes collide and leak URLs, GUIDs aren't short) and the consequences. With that written down, nobody "fixes" the retry loop thinking it's a bug.

The most important rule: an accepted ADR is never edited to change the decision. A new ADR supersedes it. The trail of decisions, and the reason behind each one, is exactly what the spike was looking for.

A doc in a pull request has a reviewer asking, "did you update this?"

Let the machine say no

So far, everything depends on people doing the right thing. Open source doesn't count on that, and not out of cynicism. Picture a maintainer receiving a pull request from a total stranger. Would you merge it without knowing whether it even builds?

Checks after merge

The problem shows up when it's already on main and everyone has pulled it.

Checks on the pull request

The problem shows up while it's still one person's branch. Red means it can't be merged.

Running the checks on the pull request has two side effects. The reviewer never has to be the bad guy about formatting or a failing test, because the machine already said no. And with required checks, the platform enforces the rule, so nobody has to remember it.

The model repository's CI runs on every pull request to main:

It builds with warnings treated as errors (a missing XML doc comment fails the build), verifies formatting, and runs the tests, including tests that check the API documentation itself. Remove a [Description] and the pull request turns red:

Failed Every_contract_property_is_described
  LinkResponse.shortUrl has no [Description].

Documentation becomes part of "done", and the one saying no is the machine.

Review culture

With the boring part automated, human review can focus on what humans are good at:

  • Small pull requests. A stranger's 2,000-line pull request doesn't get reviewed; it gets ignored.
  • Review the code, not the person. "This method…", not "you…".
  • Label your feedback, so the author knows what's blocking. Conventional Comments does this with a prefix on each comment:
issue (blocking): this accepts javascript: URLs.
suggestion: extract this into a method?
nitpick (non-blocking): extra blank line.

Labels remove the guessing, especially between people writing in a second language. And when the contributor is an AI agent, this review is what catches its mistakes.

AI agents are contributors too

Here is where the word contributor pays off: a contributor can be a person or an agent. And an agent is the ultimate newcomer, with zero context, every single time. It doesn't remember yesterday's conversation. Every session is its first day.

An agent is an intern with infinite energy and no memory. So everything that helps a stranger (the README, CONTRIBUTING, GLOSSARY, docs/ and ADRs) is also context for the agent. An agent that has read ADR 0001 won't "simplify" the retry loop away.

AGENTS.md

AGENTS.md describes itself as "a simple, open format for guiding coding agents". Think of it as CONTRIBUTING for agents: how to build, how to test, conventions, and what not to touch. Tool-specific files such as .github/copilot-instructions.md or CLAUDE.md just point to it, so the instructions don't drift apart. The model repository's boundaries:

A good issue is a good prompt

Context, expected behavior and acceptance criteria make an issue workable for anyone, human or agent. The model repository's feature template asks for them explicitly:

The checks from the previous section catch an agent's mistakes the same way they catch ours. Agents open more pull requests, so automated checks matter more, not less.

One warning: instructions generated from the code are a great start, but they age. Review them like code, and update them in the same pull request as the change they describe.

Bringing it home

None of this is exclusive to open source. It even has a name: inner source, using open-source practices inside a company, a term coined by Tim O'Reilly in 2000.

Back to the spike one last time. The output of a spike shouldn't be an answer in someone's head. It should be a file in docs/, a new ADR or a glossary entry, committed. The model repository makes that a rule:

Where to start, roughly in order of effort:

  1. A README that gets a newcomer running.
  2. A CONTRIBUTING: how we work here.
  3. Checks on the pull request, before merge.
  4. docs/ and ADRs, fed by your spikes.
  5. A GLOSSARY.
  6. An AGENTS.md.

Don't do all of it. Start with one file, in one repository, the next time you touch it. The model repository is there to copy from.

A stranger, a new intern, you in six months, an AI agent: every contributor needs the same thing, context written down in the repository. Write for strangers. Sooner or later, everyone is one.
